# Cloud-provider feasibility for pinned public-GitHub deployments

Researched 2026-09-25 from official Vercel, Render, and Cloudflare documentation. This is a documentation-only feasibility check; no provider API calls or live deployments were made. Limits and prices must be rechecked immediately before implementation and before each resource-creating action. In particular, Render's new workspace plans were rolled out to all customers by 2026-08-01, so older plan assumptions are unsafe. [Render plan rollout](https://render.com/blog/better-pricing-for-fast-growing-teams).

## Executive finding

The requested "paste any public GitHub URL, confirm a commit, then deploy to Vercel or Render" is **not equally supported by the providers' native Git integrations**. Render explicitly accepts public Git repository URLs without provider credentials. Vercel's GitHub import requires the Vercel-connected user to be the personal repository owner, or an organization owner/member with repository access; public readability alone is insufficient. Vercel's non-Git deployment API can upload files, but a bot-side fetch-at-SHA and upload implementation remains an unproven alternative for arbitrary third-party repos. [Render public repository guidance](https://render.com/docs/web-services); [Vercel GitHub import permissions](https://vercel.com/docs/git/vercel-for-github); [Vercel deployment API](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment).

**Design implication:** Do not promise arbitrary-public-repo Vercel deployment in v1 without a feasibility spike. For Vercel Git integration, reject inaccessible repos with a precise explanation or ask the user to fork into an account they own. If product requirements insist on arbitrary public repos, investigate the non-Git upload route, resource limits, and security implications before acceptance. This is an inference from the cited provider constraints, not a claim that file upload has been tested.

## Vercel

- A project may be created by API with `gitRepository`, framework, and root directory, but project creation is not equivalent to a successful deployment. A deployment API call starts a build and exposes states such as `QUEUED`, `BUILDING`, `READY`, and `ERROR`; poll for `READY` and verify the final custom-domain URL separately. [Managing projects](https://vercel.com/docs/projects/managing-projects); [Create deployment API](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment).
- GitHub repository import is permission-gated: for a personal repository the importer must be its owner; for an organization repository, an organization owner or member with repo access. A collaborator or outside collaborator does not suffice in the documented cases. Vercel Hobby also does not support connecting projects to Git repositories owned by GitHub organizations. [Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github); [Vercel limits](https://vercel.com/docs/limits).
- The create-deployment API has a `gitSource` field and a non-Git `files` pathway. Its `gitAccessToken` is documented as available **only to Vercel platform accounts**; do not assume an ordinary Vercel token can bypass Git integration permissions. Vercel explicitly documents the non-Git REST flow as hashing each file, uploading it, then creating a deployment from those references. A bot-side flow would first fetch source from an immutable GitHub SHA, and must bound repository size/file count and keep bot credentials out of provider build inputs. Whether this bot can reliably build its intended frameworks, stay within upload/build limits, and retain the agreed manual-only semantics is **unknown until a non-production spike**. [Deploying to Vercel](https://vercel.com/docs/deployments); [Create deployment API](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment); [Vercel limits](https://vercel.com/docs/limits).
- Connected Git projects deploy pushes by default. The documented way to disable all automatic deployments is `git.deploymentEnabled: false` in the repository's `vercel.json`/`vercel.ts`; a third-party repo the bot cannot edit may therefore not satisfy the agreed manual-only semantics. The Ignored Build Step can cancel builds but still counts toward deployment quotas, so it is not an equivalent clean switch. [Git configuration](https://vercel.com/docs/project-configuration/git-configuration); [Project settings](https://vercel.com/docs/project-configuration/project-settings).
- A subdomain on external DNS uses a **project-specific CNAME**, and domain status must be verified. Vercel may require a separate TXT ownership challenge if a domain is associated with another account; successful DNS publication alone is not certificate issuance. Hobby has 50 custom domains **per project**, but Hobby is restricted to personal, non-commercial use. Do not infer eligibility for every user's website from the existence of a free plan. [Add a domain](https://vercel.com/docs/domains/working-with-domains/add-a-domain); [Verify project domain API](https://vercel.com/docs/rest-api/reference/endpoints/projects/verify-project-domain); [Hobby plan](https://vercel.com/docs/plans/hobby).
- Deleting a Vercel project also deletes its deployments, assigned domains, environment variables, and settings. Remove only a project positively owned by this bot's deployment record; deleting an individual domain assignment is also supported. [Managing projects](https://vercel.com/docs/projects/managing-projects); [Remove domain](https://vercel.com/docs/domains/working-with-domains/remove-a-domain).

## Render

- Render explicitly accepts a **public Git repository URL** for a web service without Git provider credentials, including third-party public repos. Such services have no push-triggered auto-deploy or PR previews and are deployed manually. The Create Service API accepts `repo`, `branch`, `rootDir`, and `autoDeploy` fields; its documented default for `autoDeploy` is `yes`, so set `no` explicitly and confirm the resulting setting, even though the public-URL documentation says auto-deploy is unsupported. This is a documentation mismatch to test, not a reason to rely on the default. [Web services](https://render.com/docs/web-services); [Create service API](https://api-docs.render.com/reference/create-service); [Deploys](https://render.com/docs/deploys).
- The Trigger Deploy API accepts `commitId` (Git SHA). Calling that endpoint with a SHA **does not disable automatic deploys** for a linked Git service; set/verify auto-deploy off. The public-URL service and specific-SHA API are documented separately, but their exact combined behavior is **not explicitly demonstrated** in official docs found here; validate this pairing in a non-production spike. The initial service creation starts a build from the selected branch and has no documented initial-SHA field, so it may deploy branch head before a manual pinned-commit deploy; do not attach the user's custom domain until the intended commit is verified. [Trigger deploy API](https://api-docs.render.com/reference/create-deploy); [Deploys](https://render.com/docs/deploys); [Create service API](https://api-docs.render.com/reference/create-service); [Web services](https://render.com/docs/web-services).
- Render has native runtimes for Node/Bun, Python, Ruby, Go, Rust, and Elixir. .NET is supported through Docker; require a suitable Dockerfile and an app binding to the provider's `PORT` on `0.0.0.0`. [Supported languages](https://render.com/docs/language-support); [Docker](https://render.com/docs/docker); [Web services](https://render.com/docs/web-services).
- HTTP health checks can use a configured path and pass on 2xx/3xx within five seconds. New web-service instances are not routed until healthy; a failing new deploy is canceled while the previous version continues serving. The bot should still probe the final HTTPS custom-domain URL before declaring the web online. [Health checks](https://render.com/docs/health-checks); [Deploys](https://render.com/docs/deploys).
- Custom domains are supported through API add/list/verify/delete endpoints. A Cloudflare CNAME to the service's `onrender.com` hostname must start DNS-only so Render can verify ownership and issue TLS; Render says proxying may be enabled after certificate issuance, but retaining DNS-only is a valid simpler policy. Under the current workspace plans, Render Hobby includes **two** custom domains per workspace; extra domains cost **US$0.25/month each**. The new Hobby plan also caps all service types at **25 services**, includes **5 GB outbound bandwidth**, and can bill for usage over included bandwidth/build minutes if a payment method is present. Cost admission must therefore check the workspace plan, service/domain counts, and usage/spend policy, not just the compute tier. Free web services spin down after 15 minutes of inactivity; the next request can take about a minute to wake, so a single short health-check deadline could falsely mark a valid service as failed. [Add custom domain API](https://api-docs.render.com/reference/create-custom-domain); [List custom domains API](https://api-docs.render.com/reference/list-custom-domains); [Verify domain API](https://api-docs.render.com/reference/refresh-custom-domain); [Delete custom domain API](https://api-docs.render.com/reference/delete-custom-domain); [Cloudflare DNS setup](https://render.com/docs/configure-cloudflare-dns); [Custom domains and pricing](https://render.com/docs/custom-domains); [Render 2026 plan rollout and quotas](https://render.com/blog/better-pricing-for-fast-growing-teams); [Render FAQ](https://render.com/docs/faq); [Free-service behavior](https://render.com/docs/free).
- Render provides a service delete API. Deletion must be scoped to the stored service ID, with custom-domain and DNS cleanup tracked independently so a failed step remains retryable. [Delete service API](https://api-docs.render.com/reference/delete-service); [Delete custom domain API](https://api-docs.render.com/reference/delete-custom-domain).

## Cloudflare and shared lifecycle

- Cloudflare API supports creating/listing/deleting DNS records by ID, including CNAME with `proxied: false`; record comments/tags can store ownership metadata but do **not** affect DNS. Persist the Cloudflare record ID and verify name/type/content/ownership before deletion. A CNAME collision must never be overwritten. [Cloudflare DNS API](https://developers.cloudflare.com/api/resources/dns/subresources/records/); [Cloudflare record types](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/).
- If an existing `*.thienhn.io.vn` wildcard record remains, deleting an exact per-web A/CNAME record can make the wildcard answer for that name again. The promise "remove web means its subdomain no longer resolves" therefore depends on migrating retained sites to exact records and removing the wildcard after a deliberate inventory/cutover. This is an inference from Cloudflare's documented exact-record precedence over wildcard records; do not silently delete a pre-existing wildcard during an individual web removal. [Cloudflare wildcard precedence](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/).
- For Vercel, the provider supplies the project-specific CNAME target; do not hard-code a global destination. For Render, use the service's `onrender.com` target. DNS publication is not proof of build, domain verification, TLS issuance, or application health. [Vercel add domain](https://vercel.com/docs/domains/working-with-domains/add-a-domain); [Render Cloudflare setup](https://render.com/docs/configure-cloudflare-dns); [Render custom domains](https://render.com/docs/custom-domains).

## Required implementation spikes / unresolved facts

1. **Vercel arbitrary public repo:** Can an ordinary account's non-Git deployment API reliably build Vue/React source fetched at an exact SHA, without a Git connection, inside upload/build limits and without bot secrets being exposed? If not, narrow support to repositories the user's Vercel Git installation is authorized to connect (or user-owned forks). [Vercel deployment API](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment); [Vercel GitHub permissions](https://vercel.com/docs/git/vercel-for-github).
2. **Vercel manual-only pinning:** For a connected repository the bot cannot modify, determine whether any account-level/API control truly disables push-triggered deployments. The documented switch lives in the repository's config. [Git configuration](https://vercel.com/docs/project-configuration/git-configuration).
3. **Render public URL + SHA:** Test `repo` URL service creation followed by `commitId` manual deployment and verify the active commit from the deploy API before attaching DNS; official pages document the two capabilities separately, not their combination. [Create service API](https://api-docs.render.com/reference/create-service); [Trigger deploy API](https://api-docs.render.com/reference/create-deploy).
4. **Commercial use and cost guard:** Confirm account plan, current domain/service count, bandwidth/build-minute usage and spend controls, and actual site eligibility before creating Vercel/Render resources. Free-tier availability does not authorize commercial usage or extra paid resources; Render can bill usage even when every service uses a free compute instance. [Vercel Hobby](https://vercel.com/docs/plans/hobby); [Render 2026 plan rollout and quotas](https://render.com/blog/better-pricing-for-fast-growing-teams); [Render FAQ](https://render.com/docs/faq).

Until these are resolved, tickets should label the corresponding cloud path as *feasibility-gated*, not promise automatic completion for every public GitHub URL.
